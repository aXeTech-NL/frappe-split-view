# Frappe Split View — Repository Bootstrap Specification

**Repository:** `frappe-split-view`

**Frappe app/package:** `frappe_split_view`

**Display name:** Frappe Split View

**License:** MIT

**Initial target:** Frappe Framework v16

**Status:** Repository bootstrap specification for implementation by an AI coding agent

---

## 1. Purpose

Create a production-quality, open-source Frappe app that adds **Split View** as an additional generic Desk view alongside the existing List, Report, Dashboard and Kanban views.

Split View must present:

- the normal DocType list on the left;
- the selected document in a detail pane on the right;
- preferably the existing Frappe Form implementation rather than a separate preview renderer;
- a draggable pane divider;
- a full-page open action;
- predictable routing and browser history;
- a responsive fallback to normal full-page Form View.

The repository must be structured so it can later be published publicly on GitHub, used with Bench, potentially installed on Frappe Cloud, and maintained across Frappe major versions.

The project must avoid a permanent Frappe fork wherever possible.

---

## 2. Core architectural principle

Treat Split View as a **new generic Frappe Desk view type**, not as a Project-specific customization and not as a modified List View.

Conceptually:

```text
Frappe Desk
└── View Selector
    ├── List View
    ├── Report View
    ├── Dashboard View
    ├── Kanban View
    └── Split View
        ├── existing ListView
        └── existing Form/FormView
```

The app should operate mainly as a layout, lifecycle and routing orchestration layer over existing Frappe components.

The preferred approach is extension via Frappe hooks and public APIs. Direct core overrides should be avoided. If Frappe lacks a required extension point, isolate that dependency behind the smallest possible compatibility adapter.

## 7. `pyproject.toml`

`pyproject.toml` is mandatory and must be treated as the source of truth for Python package metadata and supported Frappe versions.

Frappe Cloud uses `[tool.bench.frappe-dependencies]` to validate app compatibility.

For the first development line, target Frappe v16 only.

Use a dependency declaration equivalent to:

```toml
[tool.bench.frappe-dependencies]
frappe = ">=16.0.0,<17.0.0"
```

Do not claim v17 compatibility until tested.

Use a version field that is updated as part of the release process.

Preferred initial package version:

```toml
version = "0.1.0"
```

The app is experimental before `1.0.0`.

Add development dependencies only when actually required.

## 8. Versioning strategy

Use **Semantic Versioning 2.0.0** for the app.

Format:

```text
MAJOR.MINOR.PATCH
```

Examples:

```text
0.1.0
0.2.0
0.2.1
1.0.0
1.1.0
2.0.0
```

### Rules

Before `1.0.0`:

- `0.1.0`: initial technical proof of concept;
- `0.2.0`: usable alpha/beta functionality;
- `0.x.0`: potentially breaking changes are allowed but must be documented;
- `0.x.y`: compatible bugfix release.

After `1.0.0`:

- `MAJOR`: breaking public API, configuration or supported-workflow changes;
- `MINOR`: backward-compatible functionality;
- `PATCH`: backward-compatible bugfixes.

Do not tie the app's major version directly to the Frappe major version.

For example:

```text
Frappe Split View 1.4.2
compatible with Frappe >=16,<17
```

is valid.

## 12. Recommended release roadmap

Use this as an initial planning baseline.

### `v0.1.0-alpha.1`

Goal: prove that a standard Frappe Form can coexist with an active List View.

Minimum scope:

- local app loads;
- Split View can be manually invoked;
- list renders in left pane;
- Project can render in right pane;
- no expectation of complete routing;
- document known limitations.

### `v0.1.0-alpha.2`

Goal: basic generic DocType support.

Scope:

- generic normal DocTypes;
- row selection;
- form loading;
- close detail pane;
- full-page open action;
- basic save testing.

### `v0.1.0-beta.1`

Goal: usable integration.

Scope:

- Split View appears in the Frappe View Selector;
- correct route/state handling;
- browser Back/Forward;
- draggable divider;
- persistence of pane width;
- responsive fallback;
- settings;
- core test coverage.

### `v0.1.0`

Goal: first public experimental release.

Requirements:

- installation instructions;
- compatibility matrix;
- automated CI;
- clean uninstall;
- Project, Task, Customer and at least one transactional DocType tested;
- documented known limitations.

### `v0.2.0`

Likely targets:

- wider DocType compatibility;
- improved Form lifecycle handling;
- better navigation between linked documents;
- keyboard behavior;
- performance optimization;
- improved state restoration.

### `v1.0.0`

Only release `1.0.0` after:

- Frappe v16 compatibility is considered stable;
- the app has been tested in real Desk usage;
- upgrades across several app versions have been tested;
- public configuration is considered stable;
- no known critical Form lifecycle issues remain;
- supported and unsupported DocTypes are clearly documented.

## 22. Frappe integration requirements

Frappe apps are Python packages living inside a Bench and are installed on sites through Bench.

Prefer standard Frappe extension mechanisms. Frappe's own app-authoring guidance recommends extending base behavior through framework hooks rather than unnecessarily overriding base functionality.

The implementation should therefore first investigate:

- Desk asset inclusion;
- view registration;
- route hooks or minimally invasive interception;
- List View extension points;
- Form construction and lifecycle;
- per-user settings;
- client-side state persistence.

Only introduce monkey patches when there is no viable public extension point.

All monkey patches must:

- live in a clearly named compatibility layer;
- contain comments explaining why they exist;
- reference the relevant Frappe API/code behavior;
- be covered by regression tests;
- be easy to remove if Frappe later exposes the required hook.

## 23. Split View functional requirements

Initial target behavior:

```text
┌─────────────────────────────┬─────────────────────────────────────┐
│ Standard List View          │ Standard Form View                  │
│                             │                                     │
│ record A                    │ Selected document                   │
│ record B  ← selected        │                                     │
│ record C                    │ standard controls                   │
│ record D                    │ child tables                        │
│                             │ buttons                             │
│                             │ workflow                            │
└─────────────────────────────┴─────────────────────────────────────┘
```

Required interactions:

- choose Split View from normal view selector;
- select a record;
- load document in right pane;
- select another record without destroying the list;
- preserve filters, sorting and list scroll position;
- save document;
- close detail pane;
- open document full page;
- resize divider;
- restore preferred pane width;
- fall back to full-page on narrow screens.

---

## 24. Compatibility behavior

Initially support ordinary non-special Desk DocTypes.

Potentially unsupported or separately handled types:

- Single DocTypes;
- Tree views;
- custom Pages;
- DocTypes with heavily customized client navigation;
- special system DocTypes;
- unusual form controllers that depend strongly on sole ownership of Desk state.

If a DocType cannot safely render in Split View:

1. do not crash;
2. display a clear fallback;
3. open the document in normal full-page Form View;
4. optionally record/debug-log why Split View was bypassed.

---

## 25. Routing requirements

The implementation must preserve normal browser behavior.

At minimum:

- refresh should restore the current Split View;
- browser Back/Forward should remain logical;
- full normal document routes must remain usable;
- deep links must not be broken;
- selection state should be restorable where practical.

Possible route format:

```text
/app/project/view/split
```

with state:

```text
?name=PRJ-0001
```

or an equivalent Frappe-compatible representation.

Do not finalize route syntax until current Frappe v16 routing behavior has been inspected.

## 28. Performance requirements

Avoid loading full documents for every visible list row.

Only load the active detail document.

When switching records:

- cancel/ignore stale async responses;
- clean up event listeners;
- destroy previous Form state correctly where required;
- avoid memory growth over repeated navigation.

Do not introduce polling.

Avoid forcing complete list refreshes when only the right pane changes.

---

## 29. Accessibility and keyboard use

Do not make Split View mouse-only.

Plan for:

- keyboard focus visibility;
- divider accessibility where feasible;
- predictable Tab order;
- Escape or an explicit action to close detail;
- full-page open via accessible button;
- labels/tooltips for icon-only controls.

Respect existing Frappe accessibility behavior rather than replacing it.

# Milestone 1 — Technical POC

## Objective

Determine whether the existing Frappe Form can run in a right-hand detail container while a List View remains mounted and operational.

## Implementation order

1. Inspect Frappe v16's current view selector implementation.
2. Inspect ListView creation/lifecycle.
3. Inspect FormView and `frappe.ui.form.Form`.
4. Identify global state dependencies.
5. Create a temporary Split View container.
6. Render a Project List View on the left.
7. Open one selected Project in the right pane.
8. Verify Form Scripts.
9. Verify field edits.
10. Verify Save.
11. Verify child table behavior where applicable.
12. Switch between records repeatedly.
13. Inspect event listeners and memory behavior.
14. Document all core assumptions and blockers.

Do not build the full settings UI, release automation polish or advanced UX before this POC proves the central technical assumption.

# Agent guardrails

The implementation agent must follow these constraints:

1. **Do not fork Frappe as the default solution.**
2. **Do not modify files inside the Frappe repository unless a POC proves an extension point is missing.**
3. **Do not implement a second custom form renderer unless reuse of the standard Form is demonstrably infeasible.**
4. **Do not make the app depend on ERPNext unless necessary.**
5. **Do not introduce DocType-specific logic for Project into the core architecture.**
6. **Do not claim support for Frappe versions not present in CI.**
7. **Do not introduce mutable release tags.**
8. **Do not skip tests around routing and Form lifecycle.**
9. **Do not add configuration options without a concrete use case.**
10. **Keep Frappe-version-specific workarounds inside an explicit compatibility layer.**
11. **Prefer upstreamable framework improvements over deep monkey patches when Frappe lacks a clean extension point.**
12. **Document every dependency on Frappe internals.**
